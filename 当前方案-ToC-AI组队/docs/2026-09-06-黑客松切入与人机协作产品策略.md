# COSPAN｜合拍：黑客松切入与人机协作产品策略

## 0. 结论与使用方式

**合拍以黑客松为首个完整验证场景，打通“发现队友—确认合作—人和 Agent 推进任务—共同交付”；长期发展为面向创作团队的人机协作空间。它是独立软件，胸牌与 NFC 都是可选入口。**

不是先做完一个泛社交平台，再另外做一个项目管理平台。发现负责带来适合共同做事的人，协作负责把相识转化为可验证的成果，两部分围绕同一次合作设计。

本文记录本轮战略共识，不是代码完成报告，也不更改公开发布的资质要求。第 1–4 节为方向与边界；第 5–7 节为供后续实施的方案与验收建议；第 8 节为待验证假设。

- 正式品牌和口号不变：**COSPAN｜合拍**；“人与人先相遇，人与 Agent 再共创。”
- 当前战略与阶段范围以本文和[方向决策](../../00-项目导航与方向决策.md)为准。旧文档中的“96 小时、三人排期、只交付三个启动任务”保留为早期历史，不作为本轮新承诺。
- 界面继续使用[统一产品设计规范](../10-移动端视觉与字体规范.md)，不另建一套视觉标准。
- 实现、测试、部署和真机记录统一维护在[开发与验收清单](./2026-09-06-产品上线开发与验收清单.md)。

## 1. 已确认的产品方向

| 议题 | 本轮共识 | 对产品的约束 |
| --- | --- | --- |
| 首个场景 | 黑客松是产品起点，也是一次能观察到组队与交付的完整场景 | 首次验收不能停在交换联系方式或生成任务列表 |
| 长期核心 | 人与 Agent 共同推进项目的协作空间 | 面向产品、设计、开发等创作团队，不仅是独立开发者找搭子 |
| 建联与协作 | 二者服务同一个合作目标 | 建联不自动入队；先确认共同意图和投入，再承诺任务 |
| 工具关系 | 承接飞书、GitHub 等工具之间的协调与交接 | 不重做文档编辑器、代码托管、IDE 或完整聊天体系 |
| 软硬件关系 | 合拍作为纯软件也必须独立成立 | 不要求拥有胸牌、连接设备或完成真实碰卡才能使用主链 |
| 手机与电脑 | 手机相遇与确认，电脑专业推进 | 共享身份、项目和任务数据，不要求两端界面一模一样 |
| 竞争策略 | 用具体合作场景验证价值 | 不以先在泛社交功能上全面超过 Bonjour 为前提 |

对外定位表述建议（不是本轮替换品牌口号）：

> 合拍帮助黑客松团队从找到队友到共同交付，让人和 Agent 在同一个协作空间中明确目标、确认分工、推进工作并验收成果。

长期表述可扩展为“连接人与 Agent，把分散在不同工具里的工作组织成共同交付”。首发宣传应先说明黑客松中的具体用途，不先承诺一个已经无所不能的平台。

## 2. 两条入口，同一个协作空间

```text
新关系：发现合适队友 → 双向建联 → 澄清方向与投入 → 邀请并确认入队 ┐
                                                             ├→ COSPAN Space
既有团队：直接创建项目 → 邀请现有成员 → 确认目标与成员关系 ────────┘
    → 提出任务与分工建议 → 本人接受 → 确认共同计划
    → 人执行 / 授权 Agent 执行 → 提交成果 → 人审阅与返工
    → 确认交付 → 保留协作证据 / 继续下一轮合作
```

上图是目标流程，不是现有接口全量能力声明。既有团队直入尚未打通；当前建项仍依赖活动身份，邀请仍依赖已有连接。后续需增加明确的项目邀请授权路径，不能为了直入而取消成员权限检查。

### 黑客松为什么适合先验证

- 有明确的时间窗口、交付目标和成员角色缺口，能观察合作是否真正发生。
- 从找队友到路演产物通常处于同一项目周期，便于定位流失发生在哪一步。
- 参赛者可以继续在熟悉的编辑器、飞书和 GitHub 里产出，不必迁移全部工作习惯。

边界也很明确：**比赛期间使用，不等于赛后持续使用。** 已有团队、日常设计协作和长期项目应作为后续独立验证场景，不能由一次比赛成功直接推断成立。

## 3. 合拍补的是哪些具体交接

不是简单把几个工具的链接放到一页。合拍必须回答六个问题：

1. 我们已经共同确认了什么目标，什么时候交付，什么算完成？
2. 谁愿意承担什么，哪些只是建议，哪些已经成为承诺？
3. 哪项工作依赖别人，卡在哪里，下一步由谁行动？
4. 哪个 Agent 可以读取哪些输入、使用哪些工具、消耗多少预算？
5. 人或 Agent 交出了什么，谁看过，哪些被接受，哪些需要返工？
6. 文档、代码或设计稿更新后，是否影响当前计划与验收结论？

最小例子：设计师在飞书记录需求，开发者在 GitHub 提交实现。合拍保存“这个任务引用哪版需求、谁已接受负责、Agent 基于什么输入提供辅助、哪份提交对应交付、谁确认满足标准”。不要求再把需求正文和代码复制一份。

## 4. 端侧与硬件边界

### 4.1 一个业务与数据底座，三个客户端

按用户本轮补充，正式使用“**同一底座、三类客户端**”描述结构，不使用容易与网络端口混淆的“端口”。

```text
微信小程序              手机 App                 电脑协作空间
微信能力与移动界面       安装入口与移动体验         项目推进与人机协作工作台
          └──────────────┼─────────────────┘
                   统一业务 API 与权限
                          │
           统一账号映射 / 项目成员 / 任务 / 成果
           Agent 运行与审阅 / 动态与通知事件
                          │
                 共享持久化数据与审计记录
                          │
          按授权对接模型、飞书、GitHub 等服务
```

这是目标架构及实现约束，不代表所有模块已经完成：

- **同一个人、同一份项目数据。** 微信登录、邮箱登录是身份入口，需要经过明确验证后映射到同一个内部用户 ID；不能仅凭相同昵称或头像自动合并账号。
- **核心规则在服务端统一。** 谁能入队、谁能领取、何时能启动、谁能调用 Agent 或验收，必须由后端校验，不能只在某一端隐藏按钮。
- **端不同，能力分工不同。** 共享设计规范、接口契约和可复用业务逻辑，但微信 WXML/WXSS、移动 WebView 与桌面布局不是同一套页面文件；共享底座不等于把手机页面拉宽。
- **当前实现称谓准确。** 手机安装版目前是 Android WebView 封装，不是已完成的双平台原生 App；电脑当前为 Web 工作台；手机 Web/PWA 继续作为移动体验与兼容入口，不另立一套后端。
- **同步有可验收含义。** 任一端被授权修改任务后，其余端重新读取应得到同一结果；通知推送、实时通道和连接器要独立验收，不能因“共用后端”就声称实时推送已完成。
- **机密与外部调用留在底座。** 模型密钥、外部服务凭据不写进客户端包。三端遵守相同的数据隔离、隐私与审计边界。

### 4.2 各端职责与可选硬件

| 载体 | 主要职责 | 不承担 |
| --- | --- | --- |
| 手机 Web / 安装版 / 小程序 | 发现、建联、邀请、本人接受任务、关键决定确认、进展与通知 | 把完整看板、任务编辑器和复杂权限管理塞进手机首屏 |
| 电脑 COSPAN Space | 项目选择、任务与依赖、负责人、阻塞处理、Agent 执行控制、成果审阅、关键记录 | 重建飞书、GitHub 或一套通用企业办公系统 |
| 普通胸牌 / NFC 卡 / 二维码 | 现场身份标识、打开有限资料或邀请入口 | 作为身份认证本身；扫码或读卡后自动公开隐私、自动入队 |
| 电子胸牌 | 可选设备展示与历史工厂方案联动实验 | 作为纯软件体验或商业成立的前置条件 |

“我的”应优先服务个人身份、协作证据和分享。竖向电子工牌弱化到可选设备入口是后续设计建议，**本轮未移动 UI，也未删除硬件实现**；有硬件联动需求时保留按需访问能力。

普通被动 NFC 卡由手机读取，不是两张被动卡互相交换信息。它能绕开部分手机互碰的生态限制，但仍受手机读卡能力、系统行为和落地页兼容性影响；二维码作为兼容备选。没有真实设备回执时，界面不能显示“已连接 / 已同步”。

小程序承载哪些公开功能仍取决于主体、类目、隐私和平台要求；邀请制或开发体验版不构成合规豁免。本轮不重新作法规核验，也不将产品开发完成写成公开发布已获许可。

## 5. 工具与数据边界：实施建议

以下为下一阶段方案，尚不是已接通的集成。

| 数据 / 事实 | 权威来源建议 | 合拍保存与展示 | 初期接入方式 |
| --- | --- | --- | --- |
| 需求、方案和决策正文 | 团队选定的文档工具，例如飞书 | 文档引用、关联目标、版本或读取时间、确认记录 | 先允许手动挂接授权链接，不自动读取私有正文 |
| 代码、分支、PR、CI | GitHub 等代码托管工具 | 仓库/PR/提交引用、关联任务、来源与最近核验时间 | 先引用；后续最小权限只读连接器 |
| 成员接受、任务责任、协调状态 | 无外部任务系统时由 COSPAN 管理 | 正式负责人、承诺、阻塞、计划确认和活动记录 | 复用现有 Project / Room / Task，不另建影子系统 |
| 已在外部维护的任务 | 项目明确选择的外部任务系统 | 外部任务 ID、状态映射和合拍特有的协作确认 | 先链接，接入同步前约定每个字段由谁维护 |
| Agent 执行与授权 | COSPAN 的运行记录；执行器提供原始结果 | 输入快照、运行状态、输出、费用/用量、审阅与失败记录 | 先打通一个可审计的真实能力 |
| 成果正文与验收结论 | 正文在原工具；团队验收在 COSPAN | 有版本的成果引用、审阅人、意见、接受/返工记录 | 不把 Agent 运行成功或 PR 合并自动视为团队验收 |

必须遵守的集成规则：

- **单字段单一权威来源。** 外部任务系统已是主账时，不要求团队在合拍重新手改同一状态。初期只有链接时，明确显示“未同步”，不能宣称自动交接。
- **引用不代表授权。** 输入一个链接不意味着可以读取私有仓库/文档；先确认访问者及 Agent 的权限，凭据不进入公开资料、前端资源或普通埋点。
- **先只读后写入。** 第一阶段不做无人确认的提交代码、合并、部署、发消息、发布或删除。
- **变化不能静默覆盖确认。** 外部内容更新后，旧验收仍绑定旧版本；提示需要重新核对，不覆盖历史证据。无法获取版本时记录引用与核验时间，并标明限制。
- **同步必须可恢复。** 正式连接器需处理重复事件、乱序、访问撤销和断连；显示来源与最近成功时间，失败时保留历史并允许重试。未实现前只列为验收要求。

### 协作记录的最小字段建议

沿用现有领域模型，不把本表当作数据库已有字段清单：

| 对象 | 至少需要的信息 |
| --- | --- |
| 共同目标 | 项目、目标、投入窗口、预期成果、验收标准、版本、相关成员确认 |
| 工作项 | 目标、执行方式、人类负责人及其接受记录、输入引用、依赖、状态、完成标准 |
| Agent 运行 | 任务、触发人、授权范围、输入快照/版本、执行器/模型、预算、状态、错误、输出、用量、审阅记录 |
| 成果与验收 | 任务、提交者、成果类型及引用、版本、提交时间、验收人、决定、意见、返工关联 |

区分三个事实：`任务执行完成`、`Agent 输出获认可`、`团队成果验收通过`。当前任务 `complete` 直接进入 `DONE`，不能据此宣称第三个事实已存在；下一步要设计独立成果/验收记录及兼容迁移。

## 7. 下一阶段开发顺序与验收建议

原则是**全流程连通、每段克制投入**。不先扩展泛社交信息流，也不等待通用多 Agent 平台成型。

以下为建议研发顺序，负责人尚未认领、日期未指定；不是新增的固定工期承诺。本轮由 Codex 负责文档沉淀与方案同步，不将这些开发项勾选为完成。

| 顺序 | 工作包 | 依赖 | 可观察的验收结果 |
| --- | --- | --- | --- |
| P0-A | 桌面持续任务入口与项目选择 | 复用现有任务 API；核对账号跨端恢复 | A 建项邀请 B，B 本人入队；电脑新建任务，建议负责人不自动变正式负责人；本人认领、全员确认后开始；受阻、恢复、重开与活动记录跨端一致；可正确切换项目 |
| P0-B | 成果提交与人工验收 | 明确成果/审阅对象、状态及历史 DONE 兼容策略 | 人提交有版本的链接或成果引用；授权验收人接受或要求返工；不能只点完成就假装交付已获认可；保留每轮审阅与最终产物 |
| P0-C | 一项真实 Agent 能力接入桌面 | 优先复用已有调研简报；配置、权限、预算与 P0-B 结果关联 | 负责人确认输入后触发真实调用；展示执行/失败与用量；人可审阅输出；取消、重试、重复点击不造成重复结果；Agent 审阅不替代团队验收 |
| P0-D | 黑客松跨端完整验收与受控体验准备 | P0-A/B/C、运行环境及相关发布要求 | 手机找人/建联/入队 → 电脑人机协作 → 人工验收成果 → 手机看同一结果；断网、会话过期、拒绝、权限不足均可恢复；完成分环境交付记录 |
| P1 | 既有团队直入、项目级外部引用/只读接入 | 邀请权限、字段权威来源与主链数据模型稳定 | 不强制陌生人匹配或硬件；团队原有文档/代码无需迁移；入口与断连状态真实可见 |
| 后续验证后 | 更深 Agent 执行、跨工具写入、复杂依赖、持续团队治理 | 真实使用证明价值、安全边界与成本可控 | 逐能力验收，不以功能数量或 Agent 数量代表成效 |

P0-C 中优先接通现有调研简报是实施建议，不代表已经具备自动检索、写代码或操作用户仓库能力。Agent 失败后保留人类手工推进路径。

P0-D 必须至少覆盖两个独立账号；不同端恢复同一人时也必须核对用户 ID，不能将微信身份和邮箱身份的两份账户误记为同步成功。项目选择测试需要至少两个项目，检查成员隔离及页面刷新恢复。

每个工作包分别记账：**源码完成 → 本地测试 → 后端部署 → Web/小程序/安装包交付 → 手机与电脑实测 → 用户验收 → 公开发布条件核对**。不以某一个节点代替其余节点。

## 8. 怎样验证战略，而不把愿望当成证据

现有约 30 位体验群成员是招募基础，不是有效需求、留存或产品市场匹配证明。建议先邀请少量真实黑客松团队完成一轮，例如 3–5 组；该数量只是试点建议，尚未确定时间、成员或目标值。

按一次活动/项目周期记录以下指标，同时列出样本数和分子分母；排除员工、演示与自动化测试账号：

| 问题 | 指标定义建议 | 注意事项 |
| --- | --- | --- |
| 认识是否转成合作 | 至少两名成员确认目标及投入的项目数 / 已有至少两名确认入队成员的项目数 | 不能把建联数量当作组队质量 |
| 合作是否开始 | 至少一项任务被本人认领且开始的项目数 / 已确认目标及投入的项目数 | 同时报从确认入队到首次开工的耗时 |
| 是否交付 | 有成果引用且经授权人员验收通过的项目数 / 已实际开工的项目数 | 到期与未到期项目分开，不能混用完成口径 |
| Agent 是否有帮助 | 获人工采纳的输出数 / 已进入审阅的输出数；另报失败/取消数及用量 | 采纳不等于节省时间，需要对照实际工作过程 |
| 是否减少维护负担 | 团队重复录入次数、协调耗时及为何离开合拍 | 自动回写未实现时如实记录手工步骤 |
| 赛后是否有复用价值 | 观察窗口内主动发起第二轮合作的团队数 / 已完成首轮且拥有完整观察窗口的团队数 | 时间窗口事前约定，区分比赛复赛与日常自主合作 |

不把以上指标写成“埋点已经上线”。需对照现有事件字典补充缺失事件，限制数据字段，不采集私聊、文档正文或密钥作为分析数据。

反证与应对：

- 有浏览、有连接，却不愿确认投入：先检查共同目标与参与者供需，不继续堆看板功能。
- 愿意组队却不交付：检查任务大小、时间承诺和责任接受，不能只归因为缺少 Agent。
- 做完比赛后不用：保留黑客松工具定位，单独验证常态协作需求，不宣称长期留存已成立。
- 团队觉得多维护一个平台：减少重复填写，优先修交接与权威来源，不要求把所有工具搬进合拍。

## 9. 未决问题与记录边界

- 最先接入哪一种外部工具、读哪些项目字段、采用何种授权方式，尚未最终选定。
- 成果谁来验收、能否自验、争议如何处理，需在 P0-B 前细化；Agent 输出的负责人审阅与团队交付验收不能混为一谈。
- 试点团队、活动窗口、评价阈值和后续付费方未确定。
- Bonjour 和其他协作/Agent 产品的最新能力本轮未重新查询，不能说“市面上没有”或“竞品只做社区”。差异化仍需结合既有竞品报告和真实使用验证。
